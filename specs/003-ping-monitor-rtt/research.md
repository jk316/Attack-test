# 研究记录：Ping 监控与 RTT 观测

**特性**: `specs/003-ping-monitor-rtt/` | **阶段**: 0 研究 | **日期**: 2026-11-19

本文件记录 spec.md 三个 [需要澄清] 的采纳决策与技术选型结论（格式：决策 / 理由 / 备选方案），供 plan / tasks / converge 引用。

## 澄清项决策

### 决策 1：v1 不支持多目标并行监控（澄清 003-1）

- **决策**: v1 维持单一目标监控。切换目标 = 停止旧监控 → 以新目标重新启动；同一时刻全进程最多一个监控实例、一个目标。
- **理由**: 与现状（单例 + 单一 `target_ip` + 单一样本缓冲）一致，避免引入样本归集、按目标聚合与查询接口破坏性变更；规格假设（「监控目标与攻击目标为同一 allowlist 内 IP」）与闭环实验「一次实验一个目标」的形态匹配。
- **影响与假设**: 需要监控第二目标时必须重启监控（旧样本保留在缓冲中，按时间戳查询仍可回溯）；后续版本若需要多目标，可演进为「单例 + 目标 → 缓冲映射」而不破坏现有查询接口。
- **备选方案**: 多目标 map（单例内按 IP 分缓冲）——被否决：v1 无此场景，复杂度（查询接口、停止语义、内存核算）不成比例。

### 决策 2：探测节奏纳入 experiment.json 统一配置（澄清 003-2）

- **决策**: `src/config/experiment.json` 新增 `"ping_monitor"` 配置节，字段：`probes_per_sec=10`（高分辨率模式每秒探测数）、`summary_interval_s=1`（摘要行间隔）、`fallback_interval_s=1.0`（系统 ping 回退的探测间隔，Windows 忽略）、`stats_window_s=5.0`（聚合查询默认窗口）。经 main.py 注入 `PING_MONITOR_*` 环境变量，`start()` 与命令构造在调用时读取（env 优先、缺省回落内置默认）。
- **理由**: 宪法「配置单一来源」：现状 `-p 100` / `-Q 1` / 默认 1.0 s / 5.0 s 分散在代码常量与参数默认值中，属于配置漂移；实验需要按目标环境调整探测密度（如高丢包环境降频）。
- **约束**: 探测频率下限 0.1 s（不高于 10 探针/秒）由配置校验保证，防止过频探测变成变相流量；`-p` 与 `-Q` 由配置换算，保持「每秒一次摘要」的语义一致性。
- **备选方案**: 保持内置常量——被否决：违反宪法配置单一来源，且实验无法调参。

### 决策 3：样本缓冲上限改为可配置（澄清 003-3）

- **决策**: `"ping_monitor"` 节新增 `max_samples`（默认 4000，与现状一致）；PingMonitor 实例化/启动时读取，deque 上限按配置确定。
- **理由**: 最长实验（20 s × 20 轮 + Pktgen 60 s 等待）在默认 4000 条下余量充足；但更长实验或降频场景需要按实验规模调整保留窗口；可配置消除「写死容量」的维护负担。
- **影响**: 内存 = max_samples × 样本结构大小，实施时在 quickstart 中给出量级说明（4000 条 ≈ 数百 KB）。
- **备选方案**: 固定 4000——被否决：长实验会静默淘汰旧样本，损害可观测性。

## 技术选型决策

### 决策 4：保持「fping -Q 优先 + 系统 ping 回退」双后端，不引入第三方库

- **决策**: 维持现状双后端：非 Windows 且 `fping` 在 PATH → `fping -l -Q 1 -p 100`（每秒 10 探测、每秒摘要、按周期加权收发计数）；否则系统 ping（Windows 连续模式 / Unix 连续模式）。解析继续用正则 + 子进程 stdout 行读取。
- **理由**: 现状已实现且 CLAUDE.md 认定为权威行为；fping -Q 提供 10 探针/秒的时间分辨率，是攻击窗口内观测的关键；标准库实现零新依赖、跨平台（平台差异由 `sys.platform` 探测，不硬编码命令）。
- **备选方案**: 第三方 ping 库（如 pythonping）——被否决：新增依赖、无 10 探针/秒高分辨率模式、需重新验证跨平台语义；纯 fping（无回退）——被否决：Windows 与无 fping 环境不可用。

### 决策 5：加权统计口径保持不变并写入契约

- **决策**: 丢失率 = 1 − 收到数/发送数；RTT 聚合仅统计收到探测，多探测汇总样本按其收到数加权（fping_q 周期样本 sent/received > 1）。全部丢失的摘要（fping 报 0/0/0）RTT 记为空值而非 0。
- **理由**: 现状已实现；保证两种后端在同一窗口口径下可比，是「可观测驱动」的数据基础。
- **备选方案**: 简单平均每条样本（不按收到数加权）——被否决：fping_q 周期样本会与逐探测样本不等权，统计失真。

### 决策 6：测试策略——构造输出行单测 + 真实二进制集成

- **决策**: 单元测试 mock 子进程输出，覆盖：fping -Q 摘要行/超时行解析、系统 ping 英文与中文应答/超时/不可达行解析、加权聚合口径、观测构造五类判定、并发查询、allowlist 拒绝路径、配置读取优先级；集成测试使用真实 ping/fping 二进制验证命令构造与「20 次启停无孤儿进程」（SC-006）。
- **理由**: 宪法「测试伴随」；解析与统计是可纯化验证的核心逻辑，进程生命周期必须真实验证。
- **备选方案**: 全集成（依赖真实网络）——被否决：环境不确定、不可重复。

### 决策 7：Web 控制台生命周期清理路径

- **决策**: `backend/experiment.py` 实验结束（finally 与主动 stop 流程）复用 `get_ping_monitor().stop()`，与 CLI `main.py` finally 一致。
- **理由**: FR-016 要求「实验进程正常结束时」清理；Web 模式当前缺失该调用，是规格差距 G-003。
- **备选方案**: 依赖实验重启时 start 前自动停旧——不充分：实验结束后监控会继续运行到进程退出，产生无主探测。
