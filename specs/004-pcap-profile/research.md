# 研究记录：PCAP 业务流量画像

**特性**: `specs/004-pcap-profile/` | **阶段**: 0 研究 | **日期**: 2026-11-19

本文件记录 spec.md 三个 [需要澄清] 的采纳决策与技术选型结论（格式：决策 / 理由 / 备选方案），供 plan / tasks / converge 引用。

## 澄清项决策

### 决策 1：画像 → 初始参数采用确定性映射 + 可人工覆盖（澄清 004-1）

- **决策**: 新增纯函数映射模块（`src/tools/profile_to_params.py`），把画像 JSON 确定性转换为初始流量参数，规则写入契约（contracts/pcap-profile.md）：
  - `dst_port` ← `top_dst_ports[0]`（画像无 UDP 时回落默认端口）；
  - `packet_size` ← 包长直方图中位数桶（概率累计 ≥ 50% 的首个桶）；
  - `flow_count` ← `clamp(approx_flow_count, 1, MAX_FLOW_COUNT=100)`；
  - `pps` ← 由 `iat_ms_stats.mean` 换算（`1000/mean_iat_ms`），钳制到 `[1, MAX_PPS=20000]`；
  - `duration_s` ← 维持配置默认（画像不约束时长）。
  **人工覆盖**: CLI 显式参数（`--pps / --packet-size / --flow-count / --duration`）优先于映射值；映射值只作为「未显式指定时」的初始种子注入。
- **理由**: 确定性映射可测试、可审计、可复现（宪法「数据说话」）；避免 LLM 自由发挥偏离画像导致「先画像后攻击」失效。人工覆盖保留操作员控制权，与现有 CLI 优先级语义一致。
- **备选方案**: 纯注入画像由 LLM 自由决策（现状做法）——被否决：不可测试、不可复现，验收场景（P2）无法稳定通过；全自动映射无覆盖入口——被否决：违反操作员控制预期。

### 决策 2：大文件维持顺序前 N 截断（澄清 004-2）

- **决策**: 维持现状「顺序读取前 N 包（默认 50000）即停止」，截断事实写入 notes；不做时间均匀抽样。
- **理由**: 与现状实现一致、零额外复杂度；顺序截断语义简单可预期，抓包按时间序记录时前 N 包即早期流量（偏向早期特征的风险由 notes 显式告知）；SC-002 的截断注明可直接满足。
- **演进假设**: 若后续实验发现「文件开头代表性不足」成为问题，可在 v2 增加时间范围过滤参数，不改当前口径。
- **备选方案**: 时间均匀抽样（先扫全文件再抽 N 包）——被否决：需全量扫描，破坏「防内存爆炸」初衷；随机抽样——被否决：需两次遍历或索引，复杂度不成比例。

### 决策 3：采样上限与空闲阈值可配置（澄清 004-3）

- **决策**: `experiment.json` 新增 `"pcap_profile"` 节：`max_packets=50000`、`idle_timeout_s=30`；main.py 注入 `PCAP_PROFILE_MAX_PACKETS` / `PCAP_PROFILE_IDLE_TIMEOUT_S` 环境变量；`pcap_profile` 工具与底层函数调用时读取（env 优先、回落内置默认，默认值与现状一致保证兼容）。
- **理由**: 宪法「配置单一来源」；不同业务抓包（如大流量回放文件、长会话流量）需要不同截断量与断流阈值。
- **备选方案**: 保持代码内默认常量——被否决：违反宪法配置单一来源；工具参数覆盖（仅 count 参数）——不足以覆盖空闲阈值与配置审计。

## 技术选型决策

### 决策 4：保持 Scapy rdpcap 读取，不引入新解析依赖

- **决策**: 继续使用 Scapy `rdpcap` 顺序读取 + 计数截断（现状）；PCAP 与 PCAPng 均支持；解析失败由异常捕获 → notes。
- **理由**: 现状已实现且项目以 Scapy 为技术栈（CLAUDE.md）；满足 SC-001 性能与内存目标；零新依赖。
- **备选方案**: dpkt / pyshark / tshark 子进程——被否决：新增依赖或外部进程，无必要迁移成本。

### 决策 5：流数口径修正为 5 元组（修复 src_port 缺陷）

- **决策**: 流键严格按 `(src_ip, src_port, dst_ip, dst_port, protocol)`，同一 5 元组内相邻包间隔 > `idle_timeout_s` 视为新流。现状代码流键误写 `(src_ip, src_ip, ...)`，将 src_port 位置填成 src_ip，导致同源不同端口的流被错误合并——列入差距 G-001 修正。
- **理由**: 与 task.md 原始需求、规格 FR-007 一致；近似流数是「画像反哺 flow_count」的数据基础，口径错误直接污染初始参数。
- **备选方案**: 维持现状口径——被否决：与规格矛盾，SC-005 无法通过。

### 决策 6：IAT 口径保持 (dst_ip, dst_port) 分组

- **决策**: IAT = 同一（目标 IP, 目标端口）组合内、按包时间排序后的相邻包时间差（毫秒）；单包组合不产生 IAT 值。
- **理由**: 与 task.md 原始需求（「按同一 (dst_ip,dst_port) 或同一 flow 计算，选择一种并写清楚」）及规格 FR-006 一致；现状已按此实现，测试固化即可。
- **备选方案**: 按 5 元组 flow 计算——可接受但不改变现有语义，不采纳以避免口径漂移。

### 决策 7：测试策略——构造抓包 fixture + 异常输入批测

- **决策**: 用 Scapy 生成确定性抓包（已知 IP/端口/包长/时间戳，混合 UDP/TCP/ICMP/非 IP）作为 fixture，验证七类字段、UDP-only 隔离、IAT 分组、5 元组流数、截断注明；异常输入（不存在路径、损坏文件、空文件、纯 TCP）批量调用验证零崩溃与 notes 非空；映射模块纯函数单测覆盖钳制与优先级。
- **理由**: 宪法「测试伴随」；统计口径必须用已知数据验证，SC-003~SC-006 均可由 fixture 测试直接支撑。
- **备选方案**: 依赖真实抓包文件——被否决：不可控、不可重复。
