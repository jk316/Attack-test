# 阶段 0 研究：安全约束与配置体系（横切关注点）

**特性目录**: `specs/008-security-config/` | **日期**: 2026-11-19

## 澄清决议（来自 spec.md「待澄清问题」，按 Lead 决议采纳）

### 决策 1（澄清 008-1）：禁止 --auto-approve 与实发模式组合，启动即报错

- **决策**: `--auto-approve` 与 `--pktgen-live` 或 `--trex-live` 任一同时出现时，启动即报错退出（exit≠0，输出中文原因），不进入实验循环。
- **理由**: 「自动批准 + 实发」= 无人值守的真实流量发送，违反宪法四「HITL 审批门禁」精神；在入口处互斥比运行期警告更早阻断风险。
- **备选方案**: ① 保持可用+输出警告（现状，依赖操作员自觉——否决，风险等级不可接受）；② 组合时要求二次口令确认（引入口令管理，v1 复杂度不值）。
- **注意**: `--auto-approve` 单独使用（dry-run 下）仍合法——dry-run 本就不产生流量；`--trex-explore` 与 `--trex-live` 的既有互斥保持不变。

### 决策 2（澄清 008-2）：配置默认值超上限时启动警告 + 工具内钳制

- **决策**: main.py 加载 experiment.json 后增加校验层：逐项比对默认值与宪法上限，超限项在启动时输出警告（列出「字段 → 配置值 → 钳制后上限值」）；钳制仍在工具内执行（不改变钳制语义，校验层只负责可见性）。
- **理由**: 静默钳制会掩盖配置错误（操作员以为跑的是 120 秒，实际 20 秒）；启动拒绝过于严苛（dry-run 调试场景下无害），警告+钳制是最小成本、最大可见性方案。
- **备选方案**: ① 静默钳制（现状，否决）；② 启动报错拒绝运行（阻碍无害调试）。

### 决策 3（澄清 008-3）：HITL 审批内容统一参数明细格式

- **决策**: 所有 `interrupt()` 调用点统一为 `{message, params, scope}` 结构；`scope` 取值 `scapy_traffic | pktgen_traffic | trex_script`，`params` 为该次发送的完整参数快照（TRex 保留 code_preview 与 warning 作为 params 内字段）。统一契约见 [contracts/hitl-payload.md](contracts/hitl-payload.md)。
- **理由**: 007 Web 控制台与 CLI 共用同一审批呈现路径（`_extract_hitl` 依赖 `message` 键），字段不一会导致呈现残缺、操作员决策信息不全；统一后 007 无需感知工具类型。
- **备选方案**: ① 维持现状（否决，三处字段漂移）；② 统一 + 风险分级两级展示（v2 可选，v1 统一结构已够用）。

## 技术决策

### 决策 4：上限常量为宪法级固定值，不属于可调配置

- **决策**: 参数上限（MAX_PPS 等 8 项）保持硬编码常量，不纳入 experiment.json；配置文件只能提供默认值，任何来源的值在工具内仍受常量约束（钳制）。
- **理由**: 宪法「附加约束」将上限列为固定值；若上限可配置，等于把安全边界交给配置文件（可被误改放宽），违反原则四。配置单一来源（原则六）指「默认值」单一来源，与「上限固定」是两个正交概念。
- **备选方案**: 把上限移入配置并加保护（复杂、仍可绕过）——否决。

### 决策 5：参数处置策略 = 数值钳制 + 安全违规报错

- **决策**: 数值型超限参数钳制到上限并如实报告生效值（clamp）；安全违规（非白名单、广播/组播、src_ip 非空、端口 0/>65535、非正值）直接报错拒绝（raise）。沿用现状语义（traffic_send_tool.validate_params 已如此），本特性不改动处置策略，只补缺口。
- **理由**: 钳制保证实验可收敛（LLM 超调参数不至于中断实验），报错保证安全边界零容忍；与 FR-005/FR-006 一致。
- **备选方案**: 全部报错（实验收敛性差，LLM 频繁超调会反复失败）；全部钳制（安全违规不可钳制——白名单外钳到哪都不对）。

### 决策 6：TRex 静态 IP 扫描保持「尽力而为」定位，HITL 是硬门禁

- **决策**: 静态扫描维持现状定位（可检测字面 IPv4 字面量），不做 AST 级/动态级深度扫描；在 HITL 审批内容中显式声明「静态扫描尽力而为，无法识别域名/拼接/编码构造的目标」，由操作员审阅脚本兜底。
- **理由**: 深扫描成本高且永远可被绕过（图灵完备代码）；真正的硬门禁是 HITL（人审脚本内容）+ allowlist（工具级）。与 spec FR-011 的「非硬边界」声明一致。
- **备选方案**: 引入 AST/沙箱动态追踪（v2 可选，收益不确定）。
