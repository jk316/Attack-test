# 阶段 0 研究：Web 控制台（实时实验监控与人工审批）

**特性目录**: `specs/007-web-console/` | **日期**: 2026-11-19

## 澄清决议（来自 spec.md「待澄清问题」，按 Lead 决议采纳）

### 决策 1（澄清 007-1）：不引入认证，明确声明仅限可信内网

- **决策**: v1 不实现身份认证/授权；在 README 与控制台页面增加醒目声明「仅限已授权的可信内网环境使用」，服务启动日志输出同款警告。
- **理由**: 与 CLI 一致的操作员模型；本项目为单机/实验室部署的压测工具，认证引入的密钥分发与账户管理成本远超当前威胁模型收益。宪法四（安全优先）在此场景由 HITL 门禁与 allowlist 承担，不因无认证而减损（认证缺失的风险已通过声明转移给部署方）。
- **备选方案**: ① 令牌/口令校验——增加部署配置项，v1 推迟；② 完整账号体系——明确超出范围。

### 决策 2（澄清 007-2）：单客户端会话模型（每 client_id 独立实验会话）

- **决策**: 每个 client_id 拥有独立实验会话：会话内含自己的实验运行、HITL 审批队列与启停控制；审批决定只被会话所有者（发起实验的 client_id）接受；同一 client_id 已有实验运行时拒绝其再次启动（互斥按会话粒度）。
- **理由**: 现状（进程级单例 + 任一客户端可审批/停止）存在跨窗口误操作风险；按会话隔离后，A 客户端的审批/停止无法干扰 B 客户端的实验，审批归属唯一且可审计。
- **备选方案**: ① 保持全局单实验 + 仅发起者可审批（改动小，但多窗口观察场景中第二个窗口无法开自己的实验）；② 任一客户端可审批（现状，风险最高，否决）。
- **实现影响**: backend/experiment.py 的 ExperimentManager 由进程级单例改造为 per-client_id 会话注册表；服务端在收到 hitl_response/stop_experiment 时校验发起者归属，非所有者消息返回错误提示。

### 决策 3（澄清 007-3）：PCAP 上传服务端强制类型/大小校验

- **决策**: 服务端强制校验——扩展名白名单 `.pcap/.pcapng/.cap`（不区分大小写）+ 文件大小上限 **100MB**；违反时返回结构化失败响应（含原因），文件不落盘。
- **理由**: 前端 accept 限制可被 curl/脚本绕过；无大小上限可撑爆磁盘。100MB 覆盖真实抓包画像场景且远大于典型文件，magic bytes 嗅探 v1 不做。
- **备选方案**: ① 仅前端限制（现状，不安全，否决）；② magic bytes 内容嗅探——收益低、需解析文件头，v2 再做。

## 技术决策

### 决策 4：会话重构粒度——backend 内部 per-client_id 注册表，不引入持久化/新框架

- **决策**: 在 backend/experiment.py 内把 ExperimentManager 改造为「会话注册表」模式（client_id → 会话对象），复用现有 `graph.ainvoke` → 消息推送 → HITL 队列 → `Command(resume)` 的桥接逻辑；实验状态保持进程内内存，不引入数据库/持久化。
- **理由**: 改动面收敛在 backend/；实验本就是一次性运行，重启即失可接受；避免为状态存活引入新依赖。
- **备选方案**: ① 新开 backend/sessions.py 模块——结构更清晰，但拆散现有单文件逻辑，改动面更大；② 持久化实验状态——超出规格（spec 未要求）。

### 决策 5：前端测试策略——手工验收为主，后端逻辑 pytest 覆盖，不引入前端测试框架

- **决策**: v1 不引入前端测试框架；quickstart.md 的手工验收场景作为前端验收基线；所有可服务端验证的逻辑（消息转换、会话互斥、HITL 队列、上传校验、默认值接口）以 pytest 单元/集成测试覆盖。
- **理由**: 宪法三的最低要求是「新功能至少配套单元测试」，前端为薄渲染层、无构建工具链，引入测试框架（Playwright 等）成本高、收益集中在少量 DOM 逻辑。
- **备选方案**: ① Playwright E2E——完整但重，列入 v2 可选；② 纯 JS 单测（无构建链需手搭 runner）——收益低。

### 决策 6：启动参数默认值的单一来源——新增只读默认值接口，前端加载时拉取

- **决策**: 后端新增 `GET /api/experiment/defaults`，启动时从 experiment.json 读取 `target_ip / max_iters / no_improve_limit` 返回；前端页面加载时拉取并填充表单初值；后端 `StartRequest` 的 fallback 默认也改为从同一配置读取（保持三处一致：experiment.json 是唯一来源）。
- **理由**: 宪法六「配置单一来源」；前端是静态文件直出（无模板渲染），接口拉取是引入模板引擎之外的最小方案，且天然保证后端校验与前端展示同源。
- **备选方案**: ① 模板渲染静态页（Jinja2 注入默认值）——为静态三件套引入模板层，破坏「无构建」现状；② 保持三处硬编码——违反宪法六，否决。
